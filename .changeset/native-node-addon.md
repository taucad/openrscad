Ship the engine as one package with two payloads: `@taulabs/openrscad-engine` now colocates the WebAssembly build and a native Node N-API addon, and the package's `node` export condition binds the addon when a platform package matches the host — `@taulabs/openrscad-engine-{darwin-arm64,darwin-x64,linux-x64-gnu,linux-arm64-gnu,win32-x64-msvc}`, generated by NAPI-RS from `napi.targets` and published before the root — and falls back to the in-package wasm Node build otherwise. Browsers keep resolving the wasm build; nothing the `browser`/`default` conditions reach names the loader or a Node builtin. The Node entry exports `backend` (`"native" | "wasm"`) and `backendCause` so a fallback is never silent.

The pipeline moved into a new target-agnostic `openrscad-api` crate that both `openrscad-wasm` and the new `openrscad-napi` addon marshal over, so there is one implementation and no way for the two builds to drift, and CI now asserts it: every release builds all five targets on their own runners, inspects each binary, and smoke-tests each packed tarball for byte-identical artifacts against the wasm build. Three determinism fixes make the two byte-identical on every format, including full-precision 3MF: the convex-hull horizon is a `BTreeSet` (a `HashSet` made triangle order depend on the allocator, so the same model could export two different GLBs inside one process), and both the SCAD math builtins and the geometry tessellators now use the `libm` crate instead of the platform's, which disagreed in the last f64 ULP.

The C++ Manifold kernel is now an optional `cpp-relation` feature of `openrscad-geom` (on for the CLI, the LSP, the desktop app and xtask; off for the addon and the wasm build), so the addon is pure Rust and cross-compiles without CMake; `openrscad-eval` gains a default-off `system-fonts` feature so only hosts that want OS font discovery get it. The separate `@taulabs/openrscad-engine-native` package is gone before it was ever published.
